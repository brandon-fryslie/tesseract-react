## Executive Summary

This plan provides a comprehensive, phase-by-phase modernization roadmap for bringing the tesseract-react project from a 5-7 year old stack to modern 2025 standards. The project currently uses React 16, MobX 5, Material-UI 3, and enzyme testing - all significantly outdated or deprecated.

**Current State:**
- ~3,550 LOC across 47 JavaScript files
- React 16.8.6, MobX 5, Material-UI 3, enzyme (deprecated)
- Working build pipeline (webpack 5, Jest 29, Node 20)
- Minimal test coverage (2 smoke tests)

**Target State:**
- React 18+, MobX 6, MUI 5, React Testing Library
- Full TypeScript migration
- Modern Bootstrap 5
- Comprehensive test coverage
- Zero deprecation warnings

**Total Estimated Complexity:** 8 phases, ranging from LOW to HIGH complexity per phase
**Risk Level:** HIGH if rushed, MEDIUM with phased approach
**Value:** HIGH - Future-proof, maintainable, modern DX

#### P1-3: Migrate Existing Tests

**Complexity:** MEDIUM
**Files Affected:** `src/__tests__/app.test.jsx`
**Description:**
Migrate existing enzyme tests to React Testing Library patterns. Focus on testing user-visible behavior rather than implementation details.

**Acceptance Criteria:**
- [ ] All enzyme imports replaced with RTL imports
- [ ] `mount()` replaced with `render()`
- [ ] Component existence checks replaced with accessible queries
- [ ] All tests pass with React Testing Library
- [ ] No enzyme code remains in test files
- [ ] Tests follow RTL best practices (query by role/text, not class/id)

**Technical Notes:**
```javascript
// BEFORE (enzyme)
import { mount } from 'enzyme';
const wrap = mount(<App />);
expect(wrap.find(MainContent).exists()).toBe(true);

// AFTER (RTL)
import { render, screen } from '@testing-library/react';
render(<App />);
expect(screen.getByRole('main')).toBeInTheDocument();
// OR
expect(screen.getByText(/some content/i)).toBeInTheDocument();
```

**Migration Guide:**
- Avoid querying by component type - query by accessible role or text
- Don't test internal state - test what users see
- Use `screen` queries for better error messages
- Prefer `getByRole` over `getByTestId`

// src/stores/BaseStore.ts
import { observable, action, makeObservable } from 'mobx';
import BaseModel from '../models/BaseModel';

export default abstract class BaseStore<T extends BaseModel> {
  @observable items: T[] = [];

  private static instances: Map<string, BaseStore<any>> = new Map();

  constructor() {
    makeObservable(this);
  }

  static get<T extends BaseStore<any>>(this: new () => T): T {
    const name = this.name;
    if (!BaseStore.instances.has(name)) {
      BaseStore.instances.set(name, new this());
    }
    return BaseStore.instances.get(name) as T;
  }

  @action
  addItem(item: T): void {
    this.items.push(item);
  }

  @action
  removeItem(item: T): void {
    const idx = this.items.indexOf(item);
    if (idx > -1) {
      this.items.splice(idx, 1);
    }
  }
}

## Risk Mitigation Strategies

### High-Risk Phases

**Phase 3 (MobX 6):**
- **Risk:** Breaking all state management
- **Mitigation:**
  - Use `mobx-undecorate` codemod
  - Test each store individually after updating
  - Keep side-by-side comparison branch
  - Have complete rollback plan ready
  - Test thoroughly before proceeding

**Phase 4 (MUI 5):**
- **Risk:** UI completely broken
- **Mitigation:**
  - Use MUI codemods
  - Go through v4 intermediate step
  - Run both v4 and v5 side-by-side during migration
  - Visual regression testing
  - Keep baseline screenshots for comparison

**Phase 6 (TypeScript):**
- **Risk:** Type errors blocking development
- **Mitigation:**
  - Start with loose mode (`strict: false`)
  - Allow JavaScript files during transition
  - Migrate incrementally (utils → models → stores → components)
  - Enable strict mode gradually
  - Use `any` temporarily where needed (with TODOs)

### Testing Strategy Per Phase

**After Every Phase:**
1. Run automated tests: `pnpm test`
2. Run type checking: `pnpm type-check` (Phase 6+)
3. Run linter: `pnpm lint`
4. Build production: `pnpm build`
5. Manual smoke test of all features
6. Check console for errors/warnings
7. Compare with baseline screenshots

### Rollback Triggers

**When to rollback a phase:**
- Core functionality broken and not easily fixable
- Tests failing extensively
- Performance degradation >20%
- Blocking errors preventing development
- Deadline pressure requiring stable version

**How to rollback:**
1. Revert feature branch to previous phase commit
2. Restore previous dependency versions
3. Run tests to verify stability
4. Document what went wrong
5. Plan better approach before retry
